# 玩家体验核心与关卡包装方法论

状态：当前通用关卡设计方法论。

本文档定义 Sokoban-like 单关创作的上位设计本体。它回答“这关为什么值得存在、玩家最终应体验什么、包装怎样服务该体验”，不替代 runtime、solver、graph 或原型规则文档。

## 基本命题

好关卡不是一条形式完整的因果链，也不是若干机制事件的总和。关卡首先是一段由玩家亲自见证或完成的具体体验；地图、步骤、机制组合和唯一解约束都应服务这段体验。

```text
玩家体验核心
-> 作品身份
-> 包装
-> 地图与操作
-> 硬证据验证
```

因果链仍有价值，但它属于实现层：在体验核心确定后，说明哪些状态变化必须发生、怎样被后续操作消费、工具需要验证什么。因果链不能反过来证明关卡有趣、优雅或值得进入游戏。

## 玩家体验核心

玩家体验核心描述玩家最终应亲眼看到或主动完成、并使本关值得存在的事情。它必须写成玩家可感的局面、操作与变化，不能只写机制名、事件标签或抽象主题。

至少回答：

- 玩家此前相信或预期什么；
- 开局或关键阶段出现了什么矛盾、形状或可能性；
- 玩家实际执行什么操作；
- 棋盘具体发生什么可见变化；
- 为什么这次变化值得独立成为一关。

体验核心可能是：

- 一个规则首次以完整形式被见证；
- 一个看似死局的结构被救活；
- 一个整体形状获得意外用途；
- 玩家主动制造并使用某种状态、路线、时机或几何关系；
- 两条已知规则碰撞后产生新的解释；
- 同一结构在新规则状态下产生与旧经验相反的解法。

它不要求组装机器。构造可以是构造形状，也可以是构造死角、操作面、材料状态、边界关系、顺序窗口、通路或时机。

## 作品身份

作品身份把体验核心转化为可证伪的创作承诺。它不评价作品好坏，而是规定“如果哪些关系消失，这已经不是同一关”。

作品身份应包含：

```yaml
experience_statement: 玩家具体见证或完成什么
player_action: 玩家必须亲自做什么
visible_payoff: 关键操作后哪里发生可见变化
core_boundary:
  central_objects: 体验核心本身包含哪些对象或机制
  supporting_objects: 哪些只承担包装或反馈
identity_conditions:
  - 必须保持的形状、关系、时序或对象责任
identity_counterfactuals:
  - 替换、删除或预先满足某个条件后，核心体验为什么不再成立
```

作品身份优先使用正面关系描述。例如“完整 C 形在关键操作前保持连通，凹口提供玩家操作位，上下臂在同一次刚体移动中作用于两条物体线”。不要只写禁止清单。

## 包装

包装是为了呈现、准备、揭示、兑现和收束体验核心而存在的全部结构。它包括开局构图、短测试、走位、前置准备、错误反馈、高潮与结束方式。

良好包装通常完成这些工作：

- 开局让玩家看见值得思考的对象、矛盾或形状；
- 只用必要的准备动作建立核心条件；
- 让玩家主动进入、制造或使用关键关系；
- 在关键操作后提供集中、可见的反馈；
- 高潮发生后尽快结束，不追加清理劳动；
- 关卡规模、对象数量和流程长度与回报相称。

包装不需要制造虚假难度。近乎直白的呈现也可以是完整关卡；只要它在既定角色下没有明确同题改进方向，就不应因缺少第二个洞见、额外分支或更长流程而被贬低。

## 基线版本

每个体验核心先制作一个基线版本。基线不是关卡类型，也不是低分版本；它是当前体验核心最小、完整、低风险的作品实现。

基线可以包含主动操作、状态构造或多个机制。判断它是不是基线，只看这些内容是否属于兑现当前作品身份最自然的必要组成，而不看成品能否被事后描述为 application、combination 或 challenge。

基线通过硬验证并完成必要清理后冻结。后续提高包装野心的尝试不得覆盖它。

## 相对搜索意图

基线冻结后，可以从三个方向建立独立分支。它们是画布局前声明的搜索意图，不是完成后给关卡贴的分类标签。

### Application Search

相对于基线增加玩家作者性：玩家需要主动建立体验核心成立的条件，或者在更完整的情境中使用核心。

必须写清：

- 基线直接提供了什么；
- 分支新增了哪项玩家责任；
- 如果预先满足这项责任，是否会退化回基线。

### Combination Search

相对于基线引入一个不属于体验核心的支持机制，由它创造核心所需的材料、位置、方向、入口、时机或规则状态。

有效组合要求支持机制的结果被核心实际消费。解完一个独立前置小题、相关对象全部退休、随后再开始基线关卡，不构成组合。

如果两种机制的碰撞本身成为最值得见证的事情，应建立新的体验核心，而不是继续声称它只是旧核心的包装。

### Challenge Search

在作品身份保持不变的前提下，探索难度、空间规划、构造自由度、多阶段复用、反直觉程度、玩家作者性或形式美感的上限。

Challenge 分支在设计前声明本轮挑战的维度，不要求同时提高所有维度。更多步骤、对象、事件和更长因果链不能单独证明挑战成立。

## 分支与作品集

内部可以尝试多个结构家族；机械失败、自动完成、旁路、身份死亡或只是增加流程的尝试进入 attempt log，不进入人类待玩列表。

默认交付边界：

- 一个冻结基线；
- 每种搜索意图最多两个玩家体验不同的存活分支；
- 没有自然方案的搜索意图允许为空；
- 各版本平级呈现，不由 LLM 排名或给出审美分数。

“最多两个”限制人类需要试玩的存活版本，不限制内部探索次数。

## 修订与另作

修订只解决保持体验核心、作品身份、角色与体量不变时仍然明确更好的问题。

以下属于另作，而不是当前版本的缺点：

- 把现成结构改成玩家主动组装；
- 引入新的支持机制；
- 显著提高空间规模、难度或构造自由度；
- 改变玩家最终见证的主要事情。

另作必须新建分支。成功可以成为更高野心的作品，失败直接丢弃，不得污染已冻结基线。

## 审美的非补偿性

审美判断先问是否存在明确、可感、同题可修的缺点：无意义赶路、未兑现的对象或机制、喧宾夺主的前置流程、高潮后的清理劳动、割裂子题、视觉不谐、身份弱化等。

任何明确缺点都不能靠事件覆盖、逻辑完整、难度、对象数量或其它亮点补偿。

设计野心与完成质量分开：

- 保守选择可以形成无缺点的完整作品；
- 激进分支可能达到更高上限，也可能整体失败；
- “还可以做一关更宏大的作品”不等于当前版本存在瑕疵。

LLM 不负责给存活版本作最终审美排名。人类试玩与作者判断拥有最终权威。

## 工具与结构材料

Solver、graph、replay、counterfactual 和 event probe 只验证硬事实：

- 可解性、唯一逻辑类和旁路；
- 操作与状态变化是否真实；
- 核心对象是否参与；
- 作品身份中的机械关系是否成立；
- 替换或删除关键关系后是否仍能通关。

它们不能证明关卡好玩、优雅、惊喜或应该进入哪个课程席位。

Lexicon、mechanism lab、矿工和局部结构库只提供材料。局部关系只有在被选入明确体验核心后，才拥有完整关卡的设计意义。

## 防漂移检查

每次实质修改后检查：

1. 玩家最终见证或完成的事情是否仍与体验核心相同；
2. 作品身份条件是否仍在规范解和所有允许胜解中成立；
3. 新增内容是否改变玩家与核心的关系，还是只增加流程；
4. 支持机制的结果是否被核心消费；
5. 修唯一解是否把整体形状降解成局部材料、把主动使用降解成被动动画；
6. 如果发现了另一种有趣作品，是否已经另开体验核心或分支，而不是修改原声明。

## 例子

### 主动构造成功

Reality Anchor 的 `RA_CAND_0025` 先用短前置步骤让玩家主动形成 L 形，再反复将其作为活塞使用。前置构造没有抢走主要体验，终局目标布局继续提示并消费该形状。

### 包装吞没核心

`RA_CAND_0031` 用较大地图和长前置流程触发多种机制，最终只兑现重复拉动顺序。前置对象和空间没有在主要体验中继续承担责任，形式完整不能补偿回报不足。

### 子题割裂

`RA_CAND_0032` 的前段双锚交接完成后整体退休，后段另起黏块目标题。两段各自必要仍不构成统一作品。

### 基线与分支

`RA_FRESH_2026_07_13_C_HOOK_COCKPIT_v4` 直接提供完整 C 形，构成冻结基线；`RA_EXP_2026_07_13_ASSEMBLED_COCKPIT_A3` 与 `B2` 相对于基线增加部件对齐和合舱责任，属于 application search 的不同存活分支。它们不应由 LLM 排出审美主次。

## 尚未由本方法论解决的问题

本方法论不能保证 LLM 自主发现高价值体验核心，也不能替代作者对机制、玩家知识进程和完整游戏节奏的理解。规则事实、局部结构和 runtime 探索可以扩大候选现象，但是否值得成为关卡仍需要设计判断。
